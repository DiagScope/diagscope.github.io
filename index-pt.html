Encontre o código que esconde falhas antes que a produção as revele

O DiagScope lê o código-fonte Java e Kotlin e aponta o que destrói silenciosamente as evidências de diagnóstico — exceções engolidas, transações ausentes, chamadas HTTP sem timeout. Rode no seu build Maven, deixe seu assistente de IA rodar, ou use sozinho. Nada sai da sua máquina.

No seu build Maven
$ mvn io.github.diagscope:diagscope-maven-plugin:0.1.8:scan
Standalone, com Homebrew
$ brew tap DiagScope/tap && brew install diagscope

No seu build Maven

Quebre o build, não a produção

Um plugin Maven roda o DiagScope durante o mvn verify e quebra o build conforme a tolerância que você escolheu. Está no Maven Central: nenhum repositório a adicionar e nada mais a instalar.

Adicione ao POM

Uma entrada de plugin. Sem gate configurado ele só reporta, então dá para adotar primeiro e apertar depois.

<plugin> <groupId>io.github.diagscope</groupId> <artifactId>diagscope-maven-plugin</artifactId> <version>0.1.8</version> <executions><execution> <goals><goal>scan</goal></goals> </execution></executions> </plugin>

Escolha o rigor

O mesmo diagscope.yml que vale na linha de comando vale no build. Ou decida por execução, ou por branch com um perfil.

$ mvn verify -Ddiagscope.failOn=ERROR \ -Ddiagscope.failOnConfidence=HIGH $ mvn verify -Ddiagscope.gateProfile=release

Rode uma vez

Sem editar o POM: útil para experimentar num projeto, ou como um passo próprio do pipeline.

$ mvn io.github.diagscope:diagscope-maven-plugin:0.1.8:scan \ -Ddiagscope.failOn=ERROR

O Maven roda em JDK 17 ou mais novo. Em build multi-módulo cada módulo é julgado separadamente, módulos pom são ignorados, e um único diagscope.yml na raiz vale para todos. O analisador vem com o plugin: um download de cerca de 78 MB, em cache depois.

Com assistentes de IA

Deixe seu assistente de código conferir o próprio trabalho

Quando o time gera código com um assistente, o DiagScope pode rodar antes de o assistente dizer que terminou. Assim exceções engolidas e logs ausentes são corrigidos na mesma sessão, e não em produção.

Configure uma vez

Escreve um bloco curto de instruções em AGENTS.md e CLAUDE.md e adiciona um hook do Claude Code que escaneia os arquivos alterados quando a tarefa termina. O conteúdo existente nunca é sobrescrito.

$ diagscope init-agent

Saída pensada para assistentes

Texto simples e compacto, com o pior problema primeiro e uma linha de correção para cada um. Cerca de 3 KB onde o relatório em Markdown tem 22 KB. O código de saída continua vindo do seu gate.

$ diagscope scan --format AGENT \ --files src/main/java/PaymentService.java

Escolha o rigor

A tolerância fica no diagscope.yml, então é revisada junto com o código. Falhe em erros de alta confiança, tolere alguns avisos ou defina um perfil mais rígido para branches de release.

gate: failOn: - severity: ERROR confidence: HIGH maxFindings: { WARNING: 20 }

O hook automático é para o Claude Code. Outros assistentes leem as instruções do AGENTS.md e rodam o mesmo comando, mas nada os obriga. Um scan leva de 1 a 15 segundos conforme o tamanho do projeto, por isso a checagem roda no fim da tarefa, não a cada edição. O assistente é instruído a não silenciar um problema sem perguntar a você.

Standalone

Sem dependência no seu projeto

O mesmo analisador roda sozinho. Use quando a empresa não quer um plugin no build, quando o build é Gradle, ou para olhar um repositório que não é seu. Nada é adicionado ao projeto.

Instale

O Homebrew traz o Java 17 junto. Sem Homebrew, baixe o JAR e rode com Java 17 ou mais novo.

$ brew tap DiagScope/tap $ brew install diagscope

Escaneie um projeto

Sem etapa de build. Endpoints REST, listeners Kafka e jobs agendados são encontrados como entrypoints; os relatórios ficam em target/diagscope ou build/diagscope.

$ diagscope scan --project .

Gate de CI — só ocorrências novas

Falhe o build apenas nas ocorrências introduzidas neste pull request, deixando as existentes para depois.

$ diagscope scan --project . --update-baseline $ diagscope scan --project . --baseline --fail-on ERROR

Explique uma ocorrência, consulte as regras

A descrição completa, por que importa e como corrigir; o catálogo lista todas as regras com severidade, categoria e versão.

$ diagscope explain SILENT_CATCH $ diagscope rules
O que encontra

Código que falha silenciosamente

Exceções, transações, concorrência, Kafka, performance, segurança e mais. Cada ocorrência identifica o entrypoint que chega ao problema.

SILENT_CATCH

Exceção engolida

Capturada e nunca logada ou relançada — a falha simplesmente desaparece.

FUTURE_GET_WITHOUT_TIMEOUT

Chamada bloqueante sem timeout

Uma thread fica bloqueada indefinidamente esperando um resultado que pode nunca chegar.

MISSING_TRANSACTION_ANNOTATION

Escrita sem transação

Se um passo posterior falhar, a primeira escrita é commitada e não pode ser revertida.

HTTP_TIMEOUT_NOT_SET

Chamada HTTP sem timeout

Um upstream lento esgota o pool de threads e derruba o serviço inteiro.

N_PLUS_ONE_QUERY_RISK

Query N+1 em loop

Uma chamada ao banco dentro de um loop — escala linearmente e degrada com o crescimento dos dados.

KAFKA_SEND_RESULT_IGNORED

Envio Kafka não observado

O resultado do publish é descartado — falhas ficam invisíveis para quem chamou.

Relatório

Como é o relatório

Abra o report.html em qualquer navegador. É um único arquivo autocontido: sem servidor, sem rede. Ele ordena o que corrigir primeiro, filtra por severidade e confiança e mostra o caminho de chamadas do entrypoint até cada ocorrência.
